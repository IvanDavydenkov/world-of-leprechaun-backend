# Word of Leprechaun — backend

Основа backend на Go: два независимо собираемых микросервиса с чистой архитектурой.

## Сервисы и слои

- `services/users`: пользователи, роли `user` / `admin`, сценарий входа через порт Yandex OAuth.
- `services/vpn-configs`: конфиги пользователя и скачивание через порт удалённого VPN-хоста.
- `internal/domain`: сущности и бизнес-типы, без внешних зависимостей.
- `internal/application`: сценарии и интерфейсы репозиториев / внешних систем; зависит только от domain.
- `internal/infrastructure`: настройки окружения и MongoDB-адаптеры; далее здесь будут OAuth и VPN-хост.
- `internal/transport/http`: HTTP-обработчики.
- `cmd/api`: сборка зависимостей и запуск процесса.

Сервисы не импортируют код друг друга и не обращаются к чужой БД. Идентификатор владельца конфига — непрозрачный ID пользователя из users. В дальнейшем взаимодействие идёт через явно описанные API или события. Используется MongoDB с отдельными базами `users` и `vpn_configs` и отдельными учётными записями с правами только на свою базу.

## Запуск

Требуется Go 1.26+ и доступная MongoDB. Для запуска на хосте задайте `MONGO_URI` в каждом терминале с соответствующей учётной записью и `authSource`. Базы по умолчанию: `users` и `vpn_configs`. Из корня в двух терминалах:

```powershell
go run ./services/users/cmd/api
go run ./services/vpn-configs/cmd/api
```

Проверки состояния: `/healthz` на портах 8080 и 8081 — liveness процесса; `/readyz` — доступность MongoDB (200 или 503). До открытия HTTP сервис проверяет подключение и создаёт индексы. Без MongoDB запуск завершится с ошибкой.

Или через Docker Compose (MongoDB поднимается автоматически):

```powershell
Copy-Item .env.example .env
# Заполните три отдельных случайных пароля MongoDB в .env перед запуском.
docker compose up --build
```

Compose читает `.env`. При `go run` переменные нужно установить в окружении терминала; автоматической загрузки `.env` нет.

Для паролей MongoDB в Compose используйте случайные hex-строки (например, по 64 символа): они безопасны для подстановки в URI без дополнительного URL-кодирования. Порт MongoDB на хост не опубликован. Для `go run` используйте свою доступную MongoDB либо явно добавьте локальную публикацию порта через Compose override.

Данные хранятся в томе `mongo-data`. Скрипт `deploy/mongodb/init.js` создаёт учётные записи только при первом запуске с пустым томом. Изменение паролей в `.env` не меняет пароли существующих пользователей MongoDB: их нужно отдельно обновить в базе. Не удаляйте том для смены паролей — это удалит данные.

## Окружение

| Переменная | Назначение |
| --- | --- |
| USERS_HTTP_ADDR | Адрес HTTP users, по умолчанию `:8080` |
| VPN_CONFIGS_HTTP_ADDR | Адрес HTTP vpn-configs, по умолчанию `:8081` |
| MONGO_URI | URI подключения сервиса; локально по умолчанию `mongodb://localhost:27017`, Compose задаёт аутентифицированный URI |
| MONGO_DATABASE | База сервиса: `users` или `vpn_configs` по умолчанию |
| MONGO_ROOT_USERNAME / MONGO_ROOT_PASSWORD | Начальная административная запись MongoDB, только контейнер MongoDB |
| USERS_MONGO_PASSWORD | Пароль записи users_service в Compose |
| VPN_CONFIGS_MONGO_PASSWORD | Пароль записи vpn_configs_service в Compose |
| YANDEX_CLIENT_ID | ID приложения Яндекс |
| YANDEX_CLIENT_SECRET | Секрет приложения Яндекс |
| YANDEX_REDIRECT_URL | Callback приложения Яндекс |
| VPN_HOST_ADDRESS | Адрес удалённого VPN-хоста |
| VPN_HOST_USERNAME | Имя пользователя на VPN-хосте |
| VPN_HOST_PASSWORD | Пароль на VPN-хосте |

OAuth и VPN-переменные зарезервированы и пока не используются для соединений. После подключения адаптеров они должны проверяться при старте. Секреты не коммитятся и не выводятся в логи. Доступ к VPN-хосту будет только у vpn-configs.

## Текущие границы реализации

Это ещё не готовая система авторизации. HTTP предоставляет только `GET /healthz` и `GET /readyz`. В application реализованы регистрация после подтверждения identity, вычисление актуальной роли, каталог пользователей для admin, управление жизненным циклом конфигов и скачивание с проверкой владельца. Число доступных конфигов равно числу активных выдач; отдельной квоты нет.

Нужно далее подключить: Yandex OAuth с проверкой state, обменом кода и получением identity; сессии и middleware авторизации; HTTP API; межсервисную проверку прав; SSH-адаптер и фоновую обработку операций. Подтверждён VPN-хост Ubuntu с AmneziaWG, установленной через приложение Amnezia. Для SSH нужна проверка host key; версия и контейнер уточняются по фактической установке. Содержимое конфигов содержит секреты и не должно попадать в логи.

MongoDB-адаптер пользователей использует атомарный upsert с уникальным индексом `yandex_id`; application вычисляет роль по актуальному `ADMIN_YANDEX_ID`, игнорируя сохранённое значение роли. VPN-адаптер изолирует агрегаты по owner ID в `_id`, создаёт индекс очереди незавершённых операций и хранит файлы отдельно. BSON-типы находятся только в infrastructure. При старте процессы подключаются к БД и создают индексы; бизнес-сценарии пока не вызываются из HTTP.

Требования и статус реализации: [openspec/README.md](openspec/README.md). Конфигурация OpenSpec — `openspec/config.yaml`, базовые спецификации — `openspec/specs/`. OpenSpec не заменяет будущий OpenAPI-контракт.

## Проверка

### Роли и жизненный цикл конфигов — реализация в процессе

Принятые требования находятся в `openspec/changes/admin-config-management/`. Политика admin определяется точным совпадением подтверждённого Yandex ID с `ADMIN_YANDEX_ID`; сохранённая роль не является источником полномочий. Отдельной квоты нет, новый профиль пустой.

Сценарии application поддерживают выпуск, отзыв одного/всех, мягкое удаление и повторную активацию. Удаление сначала подтверждается VPN-хостом и лишь затем фиксируется `DeletedAt`; запись остаётся в истории admin. Повторная активация сохраняет ID записи, увеличивает версию и использует новую выдачу с новым файлом. Старый отзыв не может пометить новую выдачу удалённой.

Метаданные и очередь операций хранятся в `config_accounts` с optimistic CAS по revision. Файлы хранятся отдельно в `config_files`: AES-256-GCM, случайный nonce, привязка к owner/config/generation. Открытый файл существует только в памяти при выдаче. Для этого адаптера нужен `VPN_CONFIG_ENCRYPTION_KEY` — base64 от 32 случайных байт. Ключ хранится отдельно от MongoDB; его нужно резервировать, а изменение без миграции сделает старые файлы недоступными. Автоматической ротации пока нет.

Скачивание в application использует актуальную активную выдачу из хранилища, без SSH. Старые файлы сохраняются зашифрованными, но не доступны обычному пользователю после удаления/замены. Файл одной выдачи неизменяем.

Эти сценарии ещё не подключены к HTTP: OAuth, сессии, межсервисная проверка роли, рабочий SSH Provisioner и фоновый обработчик остаются задачами изменения. Текущий executable предоставляет только health/readiness. Тестовый Provisioner используется только в тестах и не создаёт реальные VPN-конфиги. Для рабочего адаптера требуется подтвердить версию/контейнер установленной AmneziaWG и реализовать устойчивую идемпотентность выдач на хосте.

Предыдущая коллекция `configs` заменена в новом адаптере на `config_accounts`; автоматической миграции прежних записей нет. Перед использованием с существующими данными требуется отдельная миграция. Агрегат метаданных пользователя ограничен размером документа MongoDB, поэтому при росте истории потребуется её отдельное хранение.

### Команды проверки

```powershell
go test ./services/users/... ./services/vpn-configs/...
go vet ./services/users/... ./services/vpn-configs/...
go build ./services/users/... ./services/vpn-configs/...
npm exec --yes --package=@fission-ai/openspec -- openspec validate --all --strict
```

Интеграционные Go-тесты пропускаются без `MONGO_TEST_URI`. Чтобы запустить их, задайте URI отдельной тестовой MongoDB с правом создания/удаления баз и повторите `go test` с `-count=1`. Тесты создают и удаляют только свои базы с префиксом `leprechaun_test_`; проверяют конкурентную регистрацию, изоляцию конфигов, CAS и сохранение зашифрованного файла. Учётные записи сервисов из Compose этих административных прав не имеют.

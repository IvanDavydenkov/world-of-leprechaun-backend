# Модель и гарантии переключения

## Что существует сейчас
Реализован admin CRUD /admin/vpn-servers, пароль шифруется в MongoDB. Прежняя production-версия использует один host из env; новая локальная версия работает по server_id из БД. Подготовка/переключения из этого пакета реализованы локально и покрыты тестами; production-выкладка и импорт данных ещё не выполнялись. Существующие маршруты пользователей и удаления должны сохранить совместимость.

## Идентичность и данные
- Server: постоянный server_id, encrypted credentials, SSH key/fingerprint, connection revision, обнаруженные настройки, preparation state, checked_at, helper_version/hash. Переустановка Amnezia или замена хоста — новая запись, даже при повторном использовании IP.
- Binding: пара (config_id, server_id), owner_id, указатель на её текущее generation_id. Уникальность пары обеспечивается индексом/CAS. Выдача на A и выдача на B независимы и могут обе быть active.
- Generation: неизменяемые server_id, remote_id, encrypted file reference, helper journal ID и lifecycle provisioning/active/revoking/revoked. История прежних поколений остаётся. revoked никогда не возвращается в active: создаётся новое поколение.
- User config: стабильные config_id/owner_id/name, глобальный lifecycle и selected_server_id/selected_generation_id. Количество конфигов пользователя не умножается на количество серверов. version монотонно увеличивается при смене выбранного файла, включая возвращение на A; одинаковый повтор без смены файла version не меняет.
- Routing singleton: default_server_id, routing_revision, active_switch_id. Default определяет новые выдачи, а не место отзыва ранее созданных ключей. Любая операция фиксирует свой server_id/generation_id до SSH-вызова.
- Долговечные операции: actor, canonical payload hash, idempotency key, fixed plan, item claims/leases/fencing, attempts и безопасные коды ошибок. Перезапуск процесса не теряет план и не меняет зарезервированные поколения.

## Подготовка через сайт
Fingerprint из доверенной консоли — обязательная проверка перед отправкой пароля. Если передан fingerprint вместо полного public key, handshake разрешает только ED25519 и сравнивает SHA256. Полученный ключ сохраняется только при совпадении; проверка относится к точной revision и неизменной идентичности установки. TOFU, AutoAddPolicy и отключение known_hosts запрещены.

Проверяются Ubuntu, привилегии (root либо достаточный noninteractive sudo), уже установленный Docker, совместимые AWG container/interface/config/table и внешний UDP mapping. Никакие private keys/config contents не возвращаются discovery API. Контейнер и интерфейс становятся параметрами helper через валидированный JSON, а не shell-конкатенацию. При нескольких кандидатах не угадывать: вернуть needs_input и безопасный список вариантов. Public endpoint строится из подтверждённого public_host и опубликованного UDP-порта. Внутренний/private SSH host не считается автоматически публичным VPN endpoint; требуется public_host.

Helper — поставляемый backend артефакт с фиксированной версией и SHA256, а не произвольный URL из формы. Перед заменой проверяются активные процессы/операции helper; обновление под общим host-lock, с сохранением журнала /var/lib/leprechaun-awg и откатом бинарника при неуспешной проверке совместимости. Установка атомарна, root:0755; журнал root:0700, файлы 0600. Подготовка не добавляет/не отзывает peer и не переписывает awg0.conf/clientsTable. Не перезапускать контейнер ради проверки. Нельзя обновлять helper поверх неизвестного чужого файла без явной ошибки helper_conflict.

Изменение SSH key/address, credentials, endpoint, container или interface сбрасывает готовность. Изменение только name не требует повторной подготовки. Во время host-операций connection PATCH даёт 409. backend определяет готовность; frontend не выставляет ready сам. Ручная установка helper/правка env не является частью пользовательского сценария.

## Одна кнопка переключения
POST /admin/vpn-switches атомарно захватывает глобальную routing lease, проверяет expected_routing_revision и готовность target, фиксирует durable plan и назначает target default для новых выдач. Источник не нужен: пользователи могут находиться на разных серверах после частичного результата. В план попадают все глобально active конфиги на момент начала; их selected_server_id может отличаться. Deleted, deleting, creating/reactivating не активируются. Если незавершённая выдача/реактивация может позднее закончиться на старом default, старт даёт pending_config_operations/409; приём новых операций и захват switch сериализованы до фиксации default. Новые выдачи после изменения default идут на target и не увеличивают requested_count уже созданного плана.

Для каждого элемента:
1. Найти binding target. Если active, проверить наличие peer через helper без раскрытия приватного материала. При наличии peer и доступного файла использовать прежние ключи и generation_id.
2. Если binding отсутствует либо подтверждённо revoked, зарезервировать новое поколение и идемпотентно создать peer. Сохранить зашифрованный файл.
3. Если peer неожиданно отсутствует, helper journal утрачен/противоречив или файл отсутствует/не расшифровывается, не объявлять reused и не угадывать состояние. Элемент завершается конкретной ошибкой; требуется явное восстановление/перевыпуск после диагностики. Автоматическая смена ключей в такой ситуации не маскируется под возвращение.
4. Повторно проверить глобальное состояние и CAS переключить selected pointer. До этого прежний файл доступен. Ошибка target не меняет выбранный файл элемента. После успеха version увеличивается, если файл действительно изменился.
5. Не отзывать source и не считать его superseded/revoked. Возврат A→B→A использует действующий A binding, а не выдаёт новый A ключ.

Все target peer перед выбором подтверждаются сервером. Недоступный target не выбирается по наличию старого файла в БД; прежняя выбранная выдача остаётся. Если элемент уже выбран на target, повторно подтверждается peer, результат already_selected, version не меняется.

Пользователи с успешно переключёнными элементами видят новый файл сразу, остальные — прежний. Состояние active пользователя сохраняется во время switch, пока прежняя выбранная выдача active; ошибка switch не превращает его в deleted/disabled. Одна глобальная операция выполняется одновременно. При partial/failed default остаётся target; уже переключённые элементы не откатываются. Новый switch к любому ready серверу разрешён после завершения предыдущего. Retry старой операции разрешён только если с её старта не началось более новое переключение и default всё ещё её target, иначе switch_superseded/409.

Выдачи, созданные на target, но не выбранные из-за конфликта, остаются standby: это не повод автоматически отзывать их. Исключение — зарегистрированное явное глобальное удаление: его очередь обязана отозвать все выдачи, включая созданные в гонке. После удаления switch не может восстановить доступ. Предусмотреть fencing на межоперационных гонках.

## Отзыв — отдельный сценарий
Переключение НИКОГДА не запускает отзыв. scope=server отзывает выбранные bindings только указанного сервера. Чтобы не лишить пользователя выбранного файла и не допустить новых выдач на отзываемом сервере, такой запрос отклоняется целиком 409, если server является default, участвует в активном switch или выбран хотя бы одним из затронутых конфигов. Сначала переключить пользователей; для полного отключения пользователя использовать глобальное удаление.

scope=all_servers означает явное глобальное отключение выбранных config_id: блокировать скачивание/повторное использование сразу, зарегистрировать отзыв всех действующих поколений, затем ставить deleted только после подтверждённого отзыва каждого. Невозможность связаться с хостом остаётся failed/pending и не объявляется успехом. Существующие admin DELETE/bulk-delete/revoke-all получают именно эту семантику и предупреждение UI. При глобальной повторной активации после удаления выдаётся новая generation, прежние не оживают.

Удалённые записи и история не стираются физически. Нет автоотзыва по таймеру, хранению, отсутствию аренды, изменению default или уборке ошибочных переключений. Отдельной кнопки физического удаления серверов в этом объёме нет.

## Переход production с env
До включения кнопки switch нужна идемпотентная schema/data migration: зашифрованно импортировать прежний env-server, закрепить его host key и привязать ВСЕ существующие выдачи/операции к нему. Совпадение с уже созданной записью реестра должно быть явным сопоставлением администратором/оператором; не дублировать сервер и не угадывать по имени. Не читать старый хост для самого переноса метаданных. Исторические public endpoint/generation IDs и encrypted files сохраняются.

На время применения блокируются изменяющие config API и worker; чтение/скачивание допустимы. Dry-run показывает счётчики, checkpoint позволяет повтор. Продакшен-БД и ключ шифрования резервируются до изменения. После завершения все действия сайта используют MongoDB; скрытого fallback на env нет. Мастер-ключ, MongoDB и межсервисные настройки остаются в env. Этот одноразовый этап реализации/деплоя не повторяется администратором при добавлении новых серверов.

## Трафик и пользовательские устройства
Хранение истории идёт по config_id/server_id/generation_id, независимо от selected pointer. Нельзя повторно начислять старые байты при возвращении на сервер. Не реализованный сборщик трафика остаётся unavailable, утраченные данные не восстанавливаются вымышленными значениями. Неназначенные peer не включаются в план.

Переключение обновляет скачиваемый файл в кабинете; устройства сами не перенастраиваются. Download success не доказывает импорт или VPN handshake. Пользователь заново скачивает/импортирует файл. Автоматическое переключение клиентского приложения вне объёма.

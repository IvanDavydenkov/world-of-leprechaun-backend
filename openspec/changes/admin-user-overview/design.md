# Проект ответа и учёта статистики

## Status
Частично реализовано по запросу пользователя исправить GET /admin/users: профиль, vpn.counts, vpn.configs и деградация unavailable. Метаданные читаются пакетным межсервисным POST /admin/users/config-summaries с проверкой сервисного токена и актуальной роли admin. Трафик пока возвращает freshness=unavailable, coverage=unknown и null вместо байтов. Сбор трафика, импорт неназначенных peer, назначение и расширение пагинации остаются в черновике.

## HTTP-контракт
Расширить GET /admin/users?limit=50&after=<user-id>. Аутентификация — существующая сессионная cookie. Текущие права admin проверяются на каждом запросе. 401 без действующей сессии, 403 для user, 400 для неверного limit/cursor, 503 при недоступности данных пользователей или невозможности проверить права. Клиент не может передавать доверенную роль.

HTTP 200 содержит только массив, без оболочки items. Пустой результат — []. Порядок по внутреннему id, как в существующем репозитории. limit: 1..100, по умолчанию 50. Для обнаружения следующей страницы читается limit+1 запись. X-Next-Cursor возвращается только при наличии следующей страницы, содержит ID последнего возвращённого пользователя. Для frontend на другом origin этот заголовок нужно явно разрешить через Access-Control-Expose-Headers в имеющейся CORS-конфигурации. Существующие настройки origin/cookie не перезаписывать.

Все зарегистрированные пользователи, включая admin и профили без конфигов, доступны через страницы. Ответ не является глобальным транзакционным снимком users и vpn-configs. Обязателен Cache-Control: no-store.

## Профиль и конфиги
Профиль содержит только имеющиеся в users данные; новые поля Яндекса не запрашиваются. Время в UTC RFC3339.

counts.total — число постоянных записей конфигов, включая deleted и промежуточные; повторная активация не увеличивает total.
counts.active — число записей в состоянии active; это выданный доступ, а не факт подключения устройства.
counts.disabled — число записей deleted с подтверждённым отзывом.
counts.pending — creating, deleting, reactivating. Эти состояния не объявляются ни активными, ни успешно отключёнными.
Инвариант: total = active + disabled + pending.

configs содержит все постоянные записи, включая удалённые, по одному элементу на config_id. Поля: id, name, status, version. Стабильный порядок — по id. Файлы, приватные ключи, PSK, ciphertext, remote public keys и сведения SSH не возвращаются. Ошибка операции не создаёт отдельное состояние конфига: пока завершение не подтверждено, сохраняется соответствующее промежуточное состояние.

## Что считается трафиком
Трафик накапливается за всё время наблюдения в байтах для управляемых выдач AmneziaWG.
upload_bytes — отправленное пользователем: server peer RX.
download_bytes — полученное пользователем: server peer TX.
total_bytes = upload_bytes + download_bytes.

Сумма пользователя включает все config_id и все generation_id, в том числе отозванные и заменённые. Смена ключей создаёт новую generation_id, но не переносит и не повторяет показания прежней. История хранится отдельно от текущего поля Generation в ManagedConfig; текущего агрегата без истории поколений для этого недостаточно.

Это статистика туннеля по peer, не гарантированное совпадение с внешним трафиком/биллингом провайдера и не трафик Xray. Существующие неназначенные peer не приписываются пользователю автоматически; после явного назначения admin их доступная история входит в сумму этого пользователя целиком.

## Неназначенные конфиги и перенос истории
Обнаруженные существующие peer сохраняются как конфиги с owner_id=null и source=discovered. Идентичность peer определяется VPN-хостом, контейнером/интерфейсом и публичным ключом; повторная синхронизация не создаёт дубликаты и не сбрасывает уже назначенного владельца. Наличие peer на хосте означает выданный доступ, а не наличие онлайн-соединения.

До назначения такие конфиги и их трафик доступны только admin в отдельном списке, не добавляются к какому-либо пользователю и не создают фиктивного пользователя. Конкретный контракт списка и назначения нужно включить в итоговое согласование API. Назначение разрешено только admin, только существующему пользователю, только для ещё неназначенной записи. Переназначение между пользователями и снятие владельца сейчас вне области: для них потребуются отдельные правила атрибуции истории.

Подтверждено пользователем: при назначении передаётся ВСЯ доступная история конфига, включая расход до назначения. Например, 5 ГБ накоплены без владельца, после назначения ещё 2 ГБ: вклад в расход пользователя — 7 ГБ. История не обнуляется и не начинает отсчёт с момента назначения.

История расхода хранится по config_id/generation_id независимо от владельца. Назначение атомарно меняет owner_id; пользовательская сумма связывается с историей конфигов, а не начисляется повторным копированием байтов. Повтор запроса назначения тому же пользователю идемпотентен и не удваивает расход; конкурентное назначение разным пользователям допускает только одного победителя. Назначение другому владельцу возвращает конфликт. После назначения старый список неназначенных не должен продолжать показывать запись как свободную.

При первом импорте доступные текущие RX/TX учитываются один раз как начальная известная сумма, а не отбрасываются как baseline. Последующие опросы добавляют только новые приросты. Ранее накопленная история приложения не суммируется с теми же runtime-байтами повторно. Если до импорта были сбросы без сохранённых снимков, их расход неизвестен; coverage остаётся partial/unknown и не превращается в complete после назначения. observed_since обозначает начало наблюдений приложения, не дату рождения peer и не известное время начала импортированных серверных счётчиков.

У обнаруженного peer может не быть исходного клиентского файла. Публичный ключ не позволяет восстановить приватный: хранится file_available=false. Запись можно учесть и назначить без скачивания; выдача файла требует исходного файла или отдельного перевыпуска с новыми ключами. Синхронизация и назначение не создают/не удаляют peer и не меняют его ключи. Это уточняет прежний запрет на импорт готовых конфигов в admin-config-management: здесь импортируется существующая метаинформация и трафик, а не восстанавливается отсутствующий секрет.

Для configs в сводке добавляются source и file_available, чтобы admin видел происхождение и возможность скачивания. Для новых управляемых конфигов source=managed; наличие active не обещает существование скачиваемого файла у импортированной записи. Число активных конфигов пользователя увеличивается на один при назначении активного обнаруженного peer.

## Сбор и накопление
Фоновый сборщик vpn-configs читает только transfer-счётчики без приватных полей. Предпочтение команде awg show awg0 transfer, а не dump, содержащему ключи. Формат проверяется по установленным tools v3.1.20260812; перед реализацией проверить фикстурой и read-only запросом на хосте.

Источник: [официальная man-страница amneziawg-tools](https://github.com/amnezia-vpn/amneziawg-tools/blob/master/src/man/wg.8) описывает script-friendly transfer и RX/TX. Детали обработки сброса и накопления — требования нашего приложения, а не обещание источника.

Предложен интервал 60 секунд. HTTP-запрос списка не подключается по SSH и не ждёт опроса хоста. На выдачу хранить owner_id, config_id, generation_id, remote peer identity, идентификатор эпохи runtime, последние сырые RX/TX, накопленные суммы, время и качество учёта.

Обновление сырых значений и прироста должно быть атомарным. Повтор образца и параллельный обработчик не начисляют трафик дважды; запоздавший образец не откатывает накопленную сумму или baseline. Для новой управляемой выдачи учёт начинается с нуля при создании. Для существующей импортированной выдачи старт и полнота обозначаются явно, задним числом неизвестная история не выдумывается.

Новая подтверждённая эпоха runtime или уменьшение счётчика не даёт отрицательного прироста. Сохранённые накопленные суммы сохраняются, а новые наблюдаемые счётчики учитываются в новой эпохе. Один только факт уменьшения недостаточен для надёжного обнаружения всех перезапусков: механизм идентификации runtime нужно определить и протестировать отдельно. Неопределённые участки отмечаются coverage=partial.

Перед удалением peer запрашивается и сохраняется заключительное доступное показание. Ошибка статистики не должна навсегда блокировать отзыв доступа: отзыв продолжается, а полнота учёта отмечается partial. Даже заключительный опрос до удаления не обещает точного учёта байтов между опросом и удалением. Потерянные при внезапном рестарте несохранённые значения восстановить достоверно нельзя.

## Свежесть и полнота
freshness: fresh / stale / unavailable. Предложенный порог stale — 120 секунд для выдач, которые ещё способны передавать трафик. Для окончательно отозванных выдач зафиксированные итоги не устаревают просто из-за возраста; их полнота оценивается отдельно.

coverage: complete / partial / unknown. complete означает непрерывную подтверждённую историю наблюдения с начала управляемой выдачи в рамках принятой точности опроса; это не обещание точного биллинга. partial означает известный пропуск, импорт без ранней истории или неподтверждённое заключительное показание; unknown — данных для оценки ещё нет.

observed_since показывает начало доступной истории; updated_at — время последней успешной актуализации. Для сумм по нескольким незавершённым выдачам свежесть определяется по наиболее старому требуемому показанию, а не по самой свежей записи. Покрытие всей суммы не может быть лучше худшего покрытия её частей.

Профиль, у которого гарантированно никогда не было управляемых выдач, имеет counts=0, configs=[], traffic=0 с complete: отсутствие конфигов известно по данным vpn-configs. Пустая таблица показаний при существующих выдачах не считается нулевым трафиком. При частично известных суммах можно вернуть сохранённый наблюдаемый итог с coverage=partial; неизвестные части не выдаются за измеренный ноль.

## Межсервисное взаимодействие
users получает страницу профилей и одним пакетным запросом обращается к внутреннему API vpn-configs, передавая только ID этой страницы. N+1 запросов и чтения чужой MongoDB нет. Пакетный endpoint ограничен 100 ID, аутентифицирует users по серверным credentials/mTLS и не доступен по одной лишь браузерной cookie или заголовку role=admin.

Способ сервисной аутентификации выбирается при реализации с fail-closed проверкой. Недоступность проверки роли даёт отказ, а недоступность VPN-сводки после успешной проверки admin — 200 с availability=unavailable. Источник никогда не подменяет отсутствующую запись пользователя чужим агрегатом.

## Проверки
Матрица 401/403/200; все профили и пустой массив; страницы и cursor; согласованность counts; корректная детализация состояний; сохранение истории после удаления и активации; RX/TX в пользовательской перспективе; повторы/сбросы/запоздавшие образцы; частичный отзыв и ошибка последнего опроса; stale/null против нуля; пакетный API с проверкой сервиса; отсутствие VPN-секретов в ответах.

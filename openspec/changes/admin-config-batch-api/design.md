# HTTP-контракт

## Status
Контракт одобрен пользователем и реализован. Интеграционные тесты используют MongoDB и имитацию VPN-хоста; реальные peer не изменялись.

## Авторизация и границы
Все маршруты доступны только действующей сессии с актуальными правами admin. 401 без сессии, 403 для user. Для запросов с изменением состояния проверяется доверенный Origin по существующим настройкам frontend; отсутствие/несовпадение даёт 403. Пользователь и его принадлежность проверяются до SSH и записи намерений.

Публичный путь API не означает доступ к чужой БД: users подтверждает identity/роль и существование пользователя, vpn-configs выполняет операции и владеет их данными. Внутренние вызовы требуют сервисной аутентификации.

## Новая выдача
POST /admin/users/{user_id}/configs
Content-Type: application/json
Idempotency-Key: <opaque key>

Тело:
```json
{"count": 3}
```

count обязателен, целое 1..20. Дроби, строки, null, отсутствие поля и неизвестные поля отклоняются с 400. Запрос добавляет count новых постоянных записей с новыми generation_id/ключами; не меняет отдельную квоту, не назначает обнаруженные peer, не активирует deleted. При двух существующих active и count=3 после полного успеха будет пять active. Имена по умолчанию «Конфиг <короткий уникальный ID>», не связанные с порядковым номером списка.

## Удаление
Один: DELETE /admin/users/{user_id}/configs/{config_id}, без тела.
Выбранные: POST /admin/users/{user_id}/configs/bulk-delete, тело:
```json
{"config_ids": ["config-1", "config-2"]}
```
Список непустой, максимум 100 уникальных непустых ID. Дубликаты/неверная форма дают 400. Все ID должны принадлежать пользователю; если хотя бы один отсутствует или чужой, запрос целиком отклоняется с 404 до побочных эффектов. Причина не раскрывает чужого владельца.

Все: DELETE /admin/users/{user_id}/configs, без тела. Запрос «выбранные» не использует пустой массив как признак «все».

Во всех случаях: сначала подтверждённый отзыв peer на хосте, затем deleted/deleted_at в БД. Запись, версии файлов и трафик сохраняются. Уже deleted запись считается успешно обработанной без повторного создания peer. Неназначенные конфиги не затрагиваются маршрутами пользователя.

Удаление всех блокирует новые выдачи и повторную активацию для этого пользователя до завершения, включает уже принятые незавершённые создания. Новая выдача, принятая после установки блока, получает 409. Долговечное намерение, а не только память процесса, определяет порядок.

## Принятие операции
Каждый запрос изменения требует Idempotency-Key длиной 1..128 из безопасных печатных ASCII-символов без пробелов. Ключ ограничен администратором, пользователем и маршрутом операции. Сохраняется нормализованный payload: для выбранных ID используется отсортированный список, порядок не меняет смысл.

Один ключ и один смысл запроса возвращают ту же operation_id и не повторяют успешные элементы. Тот же ключ с другим count/списком ID даёт 409. Для ключа родительской пакетной выдачи заранее сохраняются все дочерние config_id/generation_id; сбой между дочерними вставками не приводит к созданию новой пачки при повторе.

Ответ на принятие:
```json
{
  "operation_id": "op-1",
  "status": "pending",
  "kind": "create",
  "requested_count": 3
}
```
HTTP 202 и Location на GET статуса. Ответ означает принятие, а не подтверждение выдачи или отключения.

## Результат
GET /admin/users/{user_id}/config-operations/{operation_id}

```json
{
  "operation_id": "op-1",
  "kind": "create",
  "status": "partial",
  "requested_count": 3,
  "succeeded_count": 2,
  "pending_count": 0,
  "failed_count": 1,
  "items": [
    {"config_id": "config-1", "status": "succeeded", "error_code": null},
    {"config_id": "config-2", "status": "succeeded", "error_code": null},
    {"config_id": "config-3", "status": "failed", "error_code": "host_operation_unconfirmed"}
  ]
}
```

Статусы родителя: pending / running / succeeded / partial / failed.
Статусы элемента: pending / running / succeeded / failed.
failed может означать неподтверждённый результат, а не отсутствие peer: сначала нужна сверка. partial/failed сохраняются для отображения и могут перейти обратно в running при безопасном повторе незавершённых элементов. succeeded_count + pending_count + failed_count = requested_count; running входит в pending_count.

Создание успешно только после подтверждения peer и сохранения зашифрованного файла. Удаление успешно только после подтверждения отзыва и сохранения deleted. При частичном успехе успешные создания не откатываются, отозванные peer не восстанавливаются. Остальные элементы обрабатываются независимо; ошибка одного не скрывает результаты других. Повтор исходного запроса с тем же Idempotency-Key возвращает ту же операцию и возобновляет только failed/pending элементы. При unknown remote outcome запрещено слепое создание новых ключей.

requested_count для выдачи равен count; для выбранных — числу уникальных запрошенных ID; для всех — числу записей, охваченных долговечной операцией, включая незавершённые создания. Если при удалении всех записей нет, возвращается та же форма операции с requested_count=0 и status=succeeded; повтор безопасен.

GET статуса возвращает 404 при отсутствии операции либо несовпадении user_id с её владельцем. Файлы, ключи, session/OAuth-токены, raw SSH-ошибки и credentials в результат не включаются. Cache-Control: no-store.

## Ошибки
400 — неверный JSON/count/список/ключ/тело запроса.
401 — отсутствует действующая сессия.
403 — не admin либо не подтверждён Origin для изменения.
404 — пользователь, конфиг или операция не найдены в указанной области.
409 — конфликт идемпотентности/жизненного цикла, активный массовый отзыв.
503 — недоступна проверка прав, нужные зависимости или хранилище намерений до принятия операции.
После сохранения операции сбой хоста отражается в её статусе, не выдаётся за общий успех и не заменяется новым operation_id.

## Проверки
Пачка ровно count новых записей; 1 и 20; неверные count; двойная отправка и изменённый payload; сбой после части созданий и рестарт; отдельный/выбранный/полный отзыв; чужой ID не вызывает частичного удаления; повтор deleted; гонка выдачи с удалением всех; сохранение истории расхода и encrypted файлов; 401/403/Origin; межсервисная аутентификация; отсутствие секретов в DTO.

## Реализация и эксплуатация
Публичные маршруты обслуживает users, а исполняет vpn-configs. Users проверяет сессию/admin/Origin, передаёт вычисленный actor_id, Idempotency-Key и тело через серверный HTTP-клиент. Браузерная cookie не пересылается. Вызов защищён INTERNAL_SERVICE_TOKEN (не менее 32 символов). VPN повторно проверяет текущую роль и существование целевого пользователя через защищённый внутренний каталог users. HTTP без TLS разрешён только для явных локальных адресов и имён сервисов Compose; вне этого контура нужен HTTPS.

Batch и все дочерние намерения сохраняются одним CAS обновлением config_accounts. Состав родителя и генерации выдач закреплены до SSH. Обработчик опрашивает очередь каждые 2 секунды. Каждая дочерняя операция получает 2-минутную lease и уникальный attempt_id; запоздавший результат прежней попытки не перезаписывает новую. После ошибки действует 30-секундная задержка; другие готовые элементы продолжают обрабатываться. Повтор исходного запроса снимает задержку только с failed элементов. Перезапуск восстанавливает просроченные lease из MongoDB.

Пока SSH Provisioner или FileVault не сконфигурированы, новый запрос получает 503 до записи намерений. Для рабочего SSH нужны установленный root-helper, адрес/пользователь/пароль, проверенный known_hosts и публичный VPN endpoint. GET статуса сохранённых операций остаётся доступным при недоступном хосте.

Ограничение текущей очереди: метаданные и история пользователя находятся в одном MongoDB-документе, как в базовом admin-config-management. При большой истории требуется её отдельное хранение. Отдельная статистика трафика из admin-user-overview в это изменение не включена; операции не удаляют конфиги, поколения и файлы физически.

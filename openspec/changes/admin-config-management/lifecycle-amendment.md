# Уточнение жизненного цикла конфигов

Статус: подтверждено пользователем, включая новые ключи при активации и зашифрованный файл в MongoDB. Требования отражены в design.md и нормативных дельтах.

## Подтверждено

- Администратор выпускает конфиг через личный кабинет: сервис подключается к VPN-хосту, создаёт конфиг и сохраняет результат в БД для последующего скачивания владельцем.
- Операционная запись о намерении может сохраняться до обращения к хосту для восстановления после сбоя. Доступным конфиг становится только после подтверждённого создания и сохранения скачиваемого файла.
- При удалении сначала отзывается доступ на VPN-сервере. Только после подтверждения запись БД помечается как удалённая.
- Запись конфигурации физически не удаляется из БД.
- При сбое отзыва запись не может считаться удалённой. Состояние операции может быть deleting/retry; это не подтверждение успешного удаления.
- Удалённая запись не доступна обычному пользователю для скачивания; администратор может инициировать её повторную активацию.
- При повторной активации должна обновляться выдаваемая версия файла в существующей записи.
- Массовое удаление применяет ту же последовательность отдельно к каждому конфигу; частичный сбой не маркирует неотозванные конфиги удалёнными.

## Ответы пользователя

1. Новый конфиг и файл в той же записи, старые ключи остаются отозванными.
2. Зашифрованный файл в MongoDB, ключ шифрования вне БД в окружении vpn-configs.

## Влияние на реализацию

Нужен явный жизненный цикл записи и версии файла; одного удаления из списка активных недостаточно. Состояния создания, удаления и повторной активации должны различать подтверждённый результат и неизвестный результат удалённой операции. Реализация этих уточнений не считается завершённой текущими заготовками очереди операций.

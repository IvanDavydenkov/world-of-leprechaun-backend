# Проект решения

## Status
Одобрено пользователем; реализация в процессе. Уточнения жизненного цикла и хранения файла подтверждены.

## Роли
users получает единственный ADMIN_YANDEX_ID из окружения. После проверки identity Яндекса роль вычисляется по точному совпадению subject с этим ID; все остальные получают user. Email, имя, порядок регистрации и входные поля клиента не определяют admin. Публичного API назначения ролей нет.

При отсутствии ADMIN_YANDEX_ID администратор не назначается. Изменение ID оператором заменяет администратора; сохранённая роль или старая сессия не должны сохранять прежние административные права. Это намеренное изменение прежней модели «хранимая роль сохраняется при входе»; сохранённое поле роли перестаёт быть источником полномочий. Детали проверки актуальности роли и отзыва сессий необходимо определить перед реализацией авторизации.

Предложение: admin имеет обычный доступ к своим конфигам плюс управление конфигами всех пользователей. Админский список пользователей содержит только необходимые для выбора данные: внутренний ID, отображаемое имя и число активных конфигов. Yandex ID не требуется показывать другим пользователям.

## Количество конфигов
Поле quota/config_limit не вводится. У нового пользователя нет назначений. Число доступных конфигов вычисляется по активным записям. Записи creating, revoking, failed не считаются доступными. Отзыв одного конфига уменьшает число доступных конфигов, массовый отзыв приводит его к нулю; после завершения можно снова выдать конфиги.

## Границы сервисов
- users: регистрация, identity, актуальная роль, каталог пользователей для admin.
- vpn-configs: метаданные, владелец, операции создания и отзыва, адаптер хоста.
- vpn-configs проверяет пользователя-цель через доверенный API users, не через чтение его MongoDB.
- Роль действующего лица подтверждается доверенным серверным механизмом; клиентские role/owner_id и произвольные HTTP-заголовки не считаются доказательством.
- Ошибка получения актуальных полномочий запрещает административную операцию.
- Учётные данные VPN-хоста доступны только vpn-configs.

## Создание
Администратор выбирает зарегистрированного пользователя и запускает создание с ключом идемпотентности. Сначала сохраняются операция и намерение создания, затем вызывается хост. Только подтверждённый конфиг становится active и доступен пользователю. Если результат вызова неизвестен, система сверяет состояние хоста, прежде чем повторять создание; слепой повтор не должен порождать дубликаты.

Адаптер должен поддерживать устойчивый идентификатор операции/удалённого объекта либо эквивалентную сверку. Если выбранный протокол этого не позволяет, дизайн уточняется до реализации. Повтор одного запроса возвращает ту же операцию; новый запрос может создать ещё один конфиг.

## Удаление
Перед отзывом конфиг переводится в revoking: скачивание через приложение прекращается. Существующий скачанный файл может работать до подтверждённого отзыва на сервере; интерфейс не должен обещать немедленное отключение при ошибке хоста.

Успех означает, что удалённая учётная сущность/peer отозвана, а постоянная запись конфига помечена deleted с временем удаления. Запись физически не удаляется. До подтверждения хоста состояние deleting не означает deleted. Подтверждённые результаты каждого конфига сохраняются отдельно при массовом отзыве. Уже отсутствующий на хосте объект считается отозванным только после достоверной проверки.

## Повторная активация и файл
Только admin активирует удалённую запись. Постоянный config_id сохраняется; каждая выдача получает новый generation_id, новые ключи и новый файл. Версия увеличивается. Старый доступ остаётся отозванным. Активация запрещена, пока для записи остаются незавершённые операции или идёт массовый отзыв.

Последовательность: сохранить намерение → создать на хосте → сохранить зашифрованный файл → подтвердить активную выдачу в метаданных. При сбое сохранения повтор использует тот же generation_id и не создаёт второго peer. Скачивание выполняется из БД без SSH. Незавершённая выдача не доступна для скачивания.

Файлы хранятся отдельно от метаданных в config_files: AES-256-GCM, случайный nonce, AAD с owner_id/config_id/generation_id и версией формата. Ключ — base64 от 32 случайных байт в VPN_CONFIG_ENCRYPTION_KEY. Файл одной выдачи неизменяем; новый файл получает новый generation_id. Старый ciphertext сохраняется для технической истории, но пользователь может скачать только актуальную активную выдачу. Ключ нужно резервировать отдельно; автоматическая ротация пока не реализована.

Для атомарности очереди и блокировки выдачи метаданные пользователя пока хранятся одним документом config_accounts с revision/CAS. Это позволяет работать с standalone MongoDB без транзакций. Большая история операций ограничена размером документа MongoDB; перед масштабированием нужно вынести историю в отдельную коллекцию с сохранением атомарности координации. Сами файлы находятся в отдельных документах и не увеличивают агрегат.

Подтверждено окружение хоста: Ubuntu, SSH, AmneziaWG через приложение Amnezia; контейнер amnezia-awg2, amneziawg-tools v3.1.20260812, awg0.conf и clientsTable в /opt/amnezia/awg/. Написан адаптер SSH и устанавливаемый root-helper с долговечным журналом generation_id, lock на хосте, обновлением peer/таблицы и awg syncconf. Helper проверяет точную версию и отказывается угадывать неизвестный формат. Исходники официального configurator/template использованы для проверки механизма. Внешний UDP endpoint задаётся отдельно от SSH-адреса.

Helper ещё не установлен на реальный хост, в executable не подключён; тесты имитируют Docker. Для серверных журналов нужны отдельное резервирование и защита root-only: до отзыва журнал содержит приватный клиентский материал. Приложение Amnezia не разделяет host-lock helper, поэтому параллельное управление клиентами из приложения и backend не поддерживается. Нативные .conf, DNS и MTU требуют проверки реальным тестовым подключением. Подробности: deploy/amnezia/README.md.

Подтверждено командой docker port: 39977/udp опубликован как 39977 на IPv4 и IPv6. Внешний VPN_PUBLIC_ENDPOINT — публичный адрес VPN-хоста с портом 39977; SSH-порт задаётся независимо в VPN_HOST_ADDRESS.

## Удаление всех
Долговечная операция массового отзыва блокирует новые выдачи этому пользователю до завершения. Она учитывает как активные конфиги, так и незавершённые создания: созданный с опозданием удалённый объект также должен быть отозван. Между несколькими экземплярами сервиса нужна координация в хранилище, а не только mutex процесса.

Каждый конфиг имеет отдельный результат. Частичный сбой не откатывает успешные отзывы и не маркируется полным успехом. Незавершённые отзывы повторяются безопасно. Завершение означает отсутствие активных конфигов и неизвестных результатов удалённых операций пользователя.

## API и безопасность
Точные маршруты и схема аутентификации будут определены после согласования поведения. Нужны сценарии: собственный профиль/список/скачивание; admin — список пользователей, список конфигов пользователя, создание, отзыв одного и всех, статус операций. Неаутентифицированным доступ запрещён; user не может выполнять admin-операции.

Операции учитывают actor_id, target_user_id, config_id, время и результат. Пароли, токены, приватные ключи и содержимое конфигов не логируются. Нужна история результатов для диагностики частичных сбоев, без хранения VPN-секретов в журнале.
